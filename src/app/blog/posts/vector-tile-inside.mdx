2016 年我第一次接触到矢量瓦片的时候，脑子里只有一个想法：这不就是把 GeoJSON 切成小块吗，有什么了不起的？

后来在项目里真正用上了，才明白这个"小块"背后藏了多少巧思。

## 栅格瓦片的困境

先说说它的前任——栅格瓦片。栅格瓦片的原理很直观：在服务端把地图渲染成一张张 256×256 的 PNG 图片，前端按需加载。技术栈简单，兼容性好，IE8 都能跑。

但问题也很明显。

第一是体积。一张 256×256 的 PNG 瓦片，即使压缩后也有 20-50KB。用户在缩放和平移时，每次都要请求几十张，总流量动辄几 MB。在 4G 信号不好的地方，地图加载体验堪称灾难。

第二是无法动态样式。瓦片是提前渲染好的图片，颜色、线宽、标注字体都写死了。产品经理说"把高速路从黄色改成红色"，你得重新切一遍瓦片。有时候只是改个色值，就要跑一整晚的切片任务。

第三是分辨率绑死。栅格瓦片在某个缩放级别下渲染的像素是固定的。用户用 Retina 屏看会觉得模糊，因为一张 256px 的图被拉伸到了 512px。

矢量瓦片就是来解决这些问题的。它不像栅格瓦片那样"存像素"，而是"存几何数据"。瓦片里装的是点、线、面的坐标，外加属性信息。前端拿到数据后自己渲染，想怎么画就怎么画。

## Mapbox Vector Tile 到底是个什么格式

Mapbox 在 2014 年开源了矢量瓦片规范，叫 Mapbox Vector Tile，后来成为了一个事实上的行业标准。大部分人说的"MVT"或者"PBF 瓦片"指的就是这个东西。

MVT 有两个关键设计选择：

**1. 用 Protocol Buffers 编码**

Protocol Buffers（简称 protobuf）是 Google 搞的一套二进制序列化协议。选它的原因很简单：紧凑。

一张包含几万条道路的矢量瓦片，用 GeoJSON 可能要 500KB，用 protobuf 编码后通常在 50KB 以内。而且解析速度明显快于 JSON——前端不需要 parse 一大坨字符串，直接按 schema 读二进制就行。

**2. 相对坐标 + 整数编码**

这是个非常精巧的设计。矢量瓦片不存绝对经纬度，而是把瓦片范围内的坐标映射到 [0, 4096] 的整数网格上。

比如一张瓦片覆盖的真实范围是 [100, 30] 到 [101, 31]，那它内部的坐标就全部归化到 0-4096 之间。这样做有两个好处：整数比浮点数省空间，而且可以进一步用 zigzag 编码压缩——相邻坐标差很小，delta 编码后大部分接近 0，压缩率极高。

实际的数据流是这样的：

```
真实经纬度
  → 瓦片内相对浮点坐标 (0.0~1.0)
    → 4096 整数网格
      → zigzag delta 编码
        → protobuf 序列化
          → gzip 压缩（HTTP 传输层）
```

每一步都在压体积。最终一个矢量瓦片通常在 10-50KB 之间，比同级别的栅格瓦片小得多。而且矢量瓦片是分辨率无关的：Retina 屏上渲染不会模糊，因为前端可以按设备像素比重新绘制。

## MVT 的内部结构

一个 .pbf 文件展开后的层级是这样的：

```
Tile
 ├── Layer "water"
 │   ├── Feature 1 (Polygon: 太平洋)
 │   │   ├── Geometry: [MoveTo(10,10), LineTo(20,10), ...]
 │   │   └── Properties: {name: "Pacific Ocean", area: 165250000}
 │   └── Feature 2 (Polygon: 大西洋)
 │       └── ...
 ├── Layer "roads"
 │   ├── Feature 3 (LineString: 京藏高速)
 │   │   ├── Geometry: ...
 │   │   └── Properties: {class: "motorway", name: "G6"}
 │   └── ...
 └── Layer "buildings"
     └── ...
```

几个值得注意的点：

Layer 是逻辑分组。一个瓦片可以包含多个 Layer，比如水系一个层、道路一个层、建筑一个层。前端可以独立控制每个层的可见性和样式。这和传统 GIS 的"图层"概念一脉相承。

Feature 的 Geometry 用的是画布指令序列，而不是坐标数组。比如 `MoveTo(10, 10), LineTo(20, 10), LineTo(20, 20)`，解码器按指令逐步移动到对应位置，形成路径。这样编码比存完整坐标数组更紧凑，因为指令类型的开销很小。

Properties 是 Key-Value 的整数索引表结构。同一个 Layer 内，所有 Feature 共享一个 Key 表和 Value 表，Feature 的 Properties 只存索引号。比如 "name" 在 Key 表里编号是 0，"class" 编号是 1，某个 Feature 的属性就是 [(0, "G6"), (1, "motorway")]。如果有 1000 条道路都叫 "G6"，"G6" 这个字符串只在 Value 表里存一次，后续全部引用索引。

这个去重设计在数据量大时效果惊人。我实测过一个全国路网的瓦片集，去重后体积缩小了约 40%。

## 是怎么切出来的

生产矢量瓦片的工具链主要有两条路：

**tilemaker**：从 OSM 的 .pbf 原始数据直接生成 MVT 瓦片。适合小规模、快速验证的场景。优点是配置简单——一个 JSON 配置文件定义哪些 OSM 标签映射到哪些图层，跑一条命令就行。缺点是面对全国级数据时内存容易爆炸，因为它需要把整个 OSM 文件全部加载到内存里做空间索引。

**T-Rex + PostGIS**：适合生产环境。T-Rex 是一个用 Rust 写的瓦片服务器，直接连 PostGIS 数据库，实时查询并生成 MVT。它的核心思路是用 ST_AsMVT 这个 PostGIS 函数在数据库层面完成聚合和编码。

标准的切片 SQL 长这样：

```sql
SELECT ST_AsMVT(q, 'roads', 4096, 'geom')
FROM (
  SELECT
    ST_AsMVTGeom(geom, ST_MakeEnvelope(100, 30, 101, 31, 4326), 4096, 256, true) AS geom,
    name, class
  FROM roads
  WHERE geom && ST_MakeEnvelope(100, 30, 101, 31, 4326)
) AS q;
```

`ST_AsMVTGeom` 负责把真实坐标映射到 4096 网格，同时裁剪掉不在瓦片范围内的部分（`true` 参数开启裁剪）。`ST_AsMVT` 负责把查询结果编码成 MVT 二进制。

还有一个细节：缓冲区。SQL 里的 `256` 是 buffer 参数，表示在瓦片边界外多取 256 个单位的几何数据。为什么需要这个？因为道路是线，线的起点可能在瓦片边界内，但线宽可能会超出边界。如果没有 buffer，瓦片边缘会出现"断线"——线条突然消失而不是平滑延伸到下一张瓦片。

前端渲染矢量瓦片时，MapLibre GL JS 会自动处理瓦片边界的拼接，让跨瓦片的线条看起来是连续的。

## 前端怎么渲染

MapLibre GL JS（Mapbox GL JS 的开源分支）是最主流的前端矢量瓦片渲染引擎。用它加载矢量瓦片非常简单：

```javascript
map.addSource('my-tiles', {
  type: 'vector',
  tiles: ['https://tiles.example.com/{z}/{x}/{y}.pbf'],
  minzoom: 0,
  maxzoom: 14
});

map.addLayer({
  id: 'roads-layer',
  type: 'line',
  source: 'my-tiles',
  'source-layer': 'roads',
  paint: {
    'line-color': '#ff6600',
    'line-width': 2
  },
  filter: ['==', 'class', 'motorway']
});
```

有意思的是，样式和数据的分离。数据源只定义了瓦片地址和缩放范围，样式完全由 `addLayer` 控制。你可以创建三个不同的图层，引用同一个数据源，分别渲染高速路、主干道和普通道路——想改颜色直接改 paint 就行，不用重新切瓦片。

这就是矢量瓦片最核心的优势：数据归数据，样式归样式。产品经理凌晨三点发消息说"把所有高速路改成荧光绿"，你只需要改一个 JSON 字段，不用半夜爬起来跑切片任务。

## 坑与经验

**坑一：MVT 不支持浮点属性**

protobuf 的 value 类型里没有 float/double，只有 string、int、bool。如果你的属性里有温度、面积之类的浮点值，要么转成整数（比如温度乘以 100 存成 int），要么转成字符串。我一般用整数方案，查询时除以 100，精度够用且传输体积小。

**坑二：瓦片内的 Feature 数量上限**

Mapbox 规范建议单个瓦片不要超过 200KB。实际经验是，如果某个瓦片包含超过 5000 个 Feature 且每个 Geometry 都很复杂（比如详尽的建筑轮廓），前端解析会明显卡顿。

解决办法通常是做要素简化——在数据库层面用 ST_Simplify 对几何做抽稀，或者在低缩放级别合并相邻的小要素。比如 z=8 时没必要渲染每个小区的每栋楼，把它们聚合成一个行政区划的面就够了。

**坑三：投影问题**

MVT 规范的默认坐标系是 EPSG:3857。如果你的原始数据是 EPSG:4326，ST_AsMVTGeom 会自动转换。但如果你用的是自定义投影（比如国内的 CGCS2000），就需要手动处理投影变换。

---

矢量瓦片不是新概念了，但它的设计理念——用空间换时间、用二进制换 JSON、用前端渲染换服务端渲染——放在今天依然很超前。理解了它的内部机制，你在做性能优化和问题排查时才能有的放矢，而不是对着一个 .pbf 文件干瞪眼。
