WebGIS 项目里最不起眼但影响最深的技术决策之一，就是数据交换格式。GeoJSON 用了快十年，几乎成了 Web 端的事实标准。但数据量一上来——几十万条记录、几百 MB 的响应体——GeoJSON 就暴露出设计上的根本问题：它是个纯文本格式，慢、大、解析耗内存。

FlatGeobuf 和 GeoParquet 这两年势头很猛，都是冲着 GeoJSON 的弱点来的。这篇文章用同一份真实数据集（中国全国道路路网，约 280 万条线段，每条带 8 个属性字段），把三种格式从文件体积到前端解析速度全部测一遍。

## 一份数据，三种格式

源数据：PostGIS 导出的道路路网，280 万条 LineString，平均每条 15 个顶点。字段包括 `road_id`、`name`、`type`、`width`、`speed_limit`、`oneway`、`surface`、`update_date`。

导出：

```bash
# GeoJSON
ogr2ogr -f GeoJSON roads.geojson PG:"dbname=gis" roads

# FlatGeobuf
ogr2ogr -f FlatGeobuf roads.fgb PG:"dbname=gis" roads

# GeoParquet
ogr2ogr -f Parquet roads.parquet PG:"dbname=gis" roads
```

## 文件体积

| 格式 | 未压缩 | Gzip 压缩 | 说明 |
|------|--------|-----------|------|
| GeoJSON | 892 MB | 78 MB | 纯文本，压缩率极高 |
| FlatGeobuf | 187 MB | 158 MB | 二进制，压缩空间有限 |
| GeoParquet | 214 MB | 176 MB | 列式存储 + Snappy 默认压缩 |

GeoJSON 的未压缩体积是 FlatGeobuf 的 4.8 倍、GeoParquet 的 4.2 倍。这个差距来自 GeoJSON 的文本开销——每个坐标都是文本数字（比如 `116.397428` 占 10 个字符 = 10 字节），加上 JSON 的语法开销（引号、逗号、花括号）。

FlatGeobuf 和 GeoParquet 用二进制存储坐标——double（8 字节）或 float（4 字节），没有文本开销。

但开了 gzip 之后差距缩小很多——GeoJSON 的冗余文本结构给了 gzip 极大的压缩空间。不过 gzip 压缩在传输层面解决的是带宽问题，解压后在前端内存里仍然是 892MB——这个"运行时体积"最终决定了浏览器的内存占用。

## 解析速度（浏览器端）

这是用户能直接感知到的指标。用同一台机器（MacBook Pro M2，Chrome 126），加载三个文件，测量从 `fetch` 开始到数据可用的时间。

| 格式 | 解析耗时 | 内存占用 | 备注 |
|------|---------|---------|------|
| GeoJSON | 8.2 秒 | ~2.8 GB | JSON.parse 在主线程，阻塞 UI |
| FlatGeobuf | 0.9 秒 | ~600 MB | 流式解析，不阻塞 |
| GeoParquet | 1.4 秒 | ~700 MB | 列式读取，可只读需要的列 |

GeoJSON 最慢且最占内存。JSON.parse 是同步操作——280 万条记录 + 坐标数组的嵌套结构，Chrome 的 JSON 解析器需要把整个字符串转成 JS 对象树，这个过程在主线程上运行，8 秒内页面完全冻结。而且内存占用约为原始文件体积的 3 倍（JSON 字符串 + JS 对象树同时存在于内存中）。

FlatGeobuf 最快，内存最省。FlatGeobuf 的设计思路是"不需要解析整个文件"——它的内部结构是一个 FlatBuffer 编码的索引头 + 连续的要素块。前端可以：
1. 先读文件头（几百字节），拿到空间范围、字段定义、要素数量
2. 用空间索引（Hilbert R-tree）快速定位到需要的要素块
3. 只解析需要的块，而不是整个文件

流式解析意味着你不需要等 280 万条数据全部加载完才能用——拿到了 1000 条就能先渲染 1000 条。而且 FlatGeobuf 使用的是 FlatBuffers 的内存布局，解码后数据直接映射到 TypedArray，不需要创建 JS 对象——Geometry 和属性都是内存零拷贝访问。

GeoParquet 居中，但有杀手锏。Parquet 是列式存储，这意味着你可以只读你需要的列。如果你只需要 `name` 和 `type` 两个字段（做分类显示），不需要读 `geometry` 列——文件体积从 214MB 缩减到大约 30MB，解析时间从 1.4 秒降到 0.3 秒。

这个"按列读取"的能力在 GIS 场景下价值巨大。很多时候前端只需要过滤条件对应的字段和坐标，不需要所有属性。GeoJSON 和 FlatGeobuf 在这方面做不到——你必须把整条记录读出来，哪怕你只需要其中两个字段。

```javascript
// GeoParquet - 只读需要的列
import { tableFromIPC } from 'apache-arrow';

const response = await fetch('/data/roads.parquet');
const buffer = await response.arrayBuffer();
const table = tableFromIPC(buffer);

// 只取 name 和 type 列
const names = table.getChild('name').toArray();
const types = table.getChild('type').toArray();

// 不加载 geometry 列，节省内存和时间
```

## 流式传输与渐进渲染

GeoJSON 的一个致命缺陷：它是单层 JSON 数组，必须完整接收才能开始解析。不能流式读取——浏览器收到一半的 JSON 字符串，`JSON.parse` 没法工作。这意味着 892MB 的文件必须全部下载完，然后再解析。

FlatGeobuf 和 GeoParquet 都支持真正的流式处理：

```javascript
// FlatGeobuf 流式加载
const response = await fetch('/data/roads.fgb');
const reader = response.body.getReader();
const deserializer = flatgeobuf.deserialize.stream();

// 边下载边解析边渲染
while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    const features = deserializer.push(value);
    features.forEach(f => map.addFeature(f));
}
```

用户看到的效果是地图上的要素逐渐出现——先出来的区域立即可交互，不用等所有数据加载完。对大数据量的 WebGIS 场景，这个体验提升是质的改变。

## 属性查询性能

GIS 不只是画图，还要查属性。假设一个场景：280 万条道路中找出所有"speed_limit > 80 的高速公路"。

| 格式 | 查询耗时 | 说明 |
|------|---------|------|
| GeoJSON | 0.4 秒 | 遍历 280 万个 JS 对象，每个访问 `.properties.speed_limit` |
| FlatGeobuf | 0.3 秒 | 遍历 TypedArray，属性访问是数组索引 |
| GeoParquet | 0.02 秒 | 列式扫描 + 谓词下推，只扫描 `speed_limit` 列 |

GeoParquet 在这里吊打另外两个。列式存储 + 谓词下推意味着它只扫描 `speed_limit` 列，而且是压缩的、向量化的批量扫描。FlatGeobuf 比 GeoJSON 稍快——因为 TypedArray 比 JS 对象属性访问快一个数量级，而且没有 GC 压力。

但如果查询需要同时访问 geometry（比如"speed_limit > 80 且长度大于 2 公里"），FlatGeobuf 和 GeoJSON 的优势会回升——它们不需要跨列 JOIN。GeoParquet 需要同时读取 geometry 和 speed_limit 两列然后在内存里做匹配。

## 生态与工具

| | GeoJSON | FlatGeobuf | GeoParquet |
|---|---|---|---|
| GDAL/OGR 读写 | ✅ | ✅ | ✅ |
| QGIS 支持 | ✅ | ✅ (3.20+) | ✅ (3.28+) |
| PostGIS 导入 | ✅ | ⚠️ ogr2ogr | ⚠️ ogr2ogr |
| OpenLayers 支持 | ✅ 原生 | ✅ 插件 | ❌ |
| MapLibre 支持 | ✅ 原生 | ❌ | ❌ |
| Leaflet 支持 | ✅ 原生 | ❌ | ❌ |
| Python (geopandas) | ✅ | ✅ | ✅ |
| 浏览器端库 | 原生 JSON.parse | flatgeobuf (32KB) | apache-arrow (150KB) |

生态上 GeoJSON 还是遥遥领先——它是 Web 端的"英语"，所有 GIS 工具都支持。FlatGeobuf 的地图框架支持正在追赶（OL 已有社区插件，MapLibre 和 Leaflet 还没有官方支持）。GeoParquet 目前在浏览器端的支持最弱——需要引入 Apache Arrow 的 JavaScript 库（150KB gzipped），而且没有现成的 map 图层适配器。

## 选型建议

**GeoJSON**：API 默认格式。前后端分离项目里，后端输出 GeoJSON，前端什么库都不装就能用。数据量在 1 万条以下时，GeoJSON 的性能影响可以忽略。超过 10 万条时开始成为瓶颈。

**FlatGeobuf**：需要替换 GeoJSON 的第一个候选。文件小、解析快、支持流式、生态在增长。如果你的后端是 GDAL 生态（PostGIS + ogr2ogr），输出 FlatGeobuf 只改一个参数。前端引入 `flatgeobuf` 库（32KB），比 GeoJSON 的零依赖稍微多点，但完全值得。

**GeoParquet**：数据科学和空间分析场景的首选。如果你做的是一个数据分析平台而不是地图展示系统——用户上传数据做空间分析、分类、聚合——GeoParquet 的列式存储和谓词下推是 Game Changer。但它在地图框架中的集成度最低，需要自己写适配层。

一个实际的组合方案：后端同时提供三种格式的 API endpoint。前端根据数据量和操作类型自动选择——数据量小用 GeoJSON（零开销），量大需要渲染用 FlatGeobuf（流式快），做分析查询用 GeoParquet（列式扫描）。

这不是过度工程化。三种格式的输出可以共用同一个 GDAL 数据源，后端只是多写了几个 ogr2ogr 导出配置，维护成本极低。前端的加载逻辑也很简单——判断 `featureCount > 50000` 就切到 FlatGeobuf，判断"用户在做聚合查询"就切到 GeoParquet。
