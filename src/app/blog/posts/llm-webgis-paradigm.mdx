2025 年底我开始认真尝试把大模型接入 WebGIS 项目。最初的动机很简单：甲方永远觉得地图操作太复杂。"我要看朝阳区上个月销售额超过 100 万的门店"——这句话对业务人员来说只需要 3 秒说出来，但在传统 WebGIS 里，需要先选行政区划、再设筛选条件、再选时间范围、再点查询。四步操作，至少 30 秒。

能不能直接说一句话，地图就自动完成操作？能，而且实现起来比想象中简单。

## 整体思路

```
用户输入自然语言
    │
    ▼
LLM（解析意图，生成空间查询参数）
    │
    ▼
前端（把参数转成地图操作：缩放、筛选、高亮）
    │
    ▼
地图响应
```

LLM 不直接操作地图。它只负责理解用户意图，输出结构化的操作指令。前端拿指令执行。这个架构的好处是 LLM 和地图解耦——换模型、换地图引擎、加新操作类型，都不影响另一端。

## Function Calling：让 LLM 输出结构化指令

LLM 本身输出的是自由文本，没法直接驱动代码。Function Calling 解决了这个问题——你定义一组"函数"，告诉 LLM 每个函数是干什么的、参数是什么，LLM 会在需要时输出 JSON 格式的函数调用。

定义几个地图操作函数：

```javascript
const tools = [
    {
        type: 'function',
        function: {
            name: 'flyTo',
            description: '飞行定位到指定位置',
            parameters: {
                type: 'object',
                properties: {
                    location: {
                        type: 'string',
                        description: '地点名称，如"北京市朝阳区"'
                    },
                    zoom: {
                        type: 'number',
                        description: '缩放级别'
                    }
                },
                required: ['location']
            }
        }
    },
    {
        type: 'function',
        function: {
            name: 'filterMarkers',
            description: '按条件筛选地图上的标记点',
            parameters: {
                type: 'object',
                properties: {
                    field: {
                        type: 'string',
                        description: '筛选字段，如 sales、region、type'
                    },
                    operator: {
                        type: 'string',
                        enum: ['>', '<', '=', '>=', '<='],
                        description: '比较运算符'
                    },
                    value: {
                        type: 'string',
                        description: '筛选值'
                    }
                },
                required: ['field', 'operator', 'value']
            }
        }
    },
    {
        type: 'function',
        function: {
            name: 'heatmapByField',
            description: '按指定字段生成热力图',
            parameters: {
                type: 'object',
                properties: {
                    field: {
                        type: 'string',
                        description: '热力图权重字段，如 sales、population'
                    }
                },
                required: ['field']
            }
        }
    }
];
```

然后调 LLM：

```javascript
const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
        model: 'gpt-4',
        messages: [
            {
                role: 'system',
                content: `你是 WebGIS 系统的自然语言助手。
                当前可用数据字段：name（门店名）、sales（销售额，万元）、region（区域）、type（类型）。
                当前地图范围：北京市。`
            },
            {
                role: 'user',
                content: '显示朝阳区销售额超过100万的门店'
            }
        ],
        tools: tools,
        tool_choice: 'auto'
    })
});

const data = await response.json();
const toolCalls = data.choices[0].message.tool_calls;
```

`system` prompt 里告诉 LLM 当前的数据字段和地图范围，这样它知道 `field` 可以填什么、哪些字段存在。不传这个上下文，LLM 可能会编造不存在的字段名。

对于"显示朝阳区销售额超过100万的门店"这句话，LLM 会返回两个函数调用：

```json
[
    {
        "name": "flyTo",
        "arguments": { "location": "北京市朝阳区", "zoom": 12 }
    },
    {
        "name": "filterMarkers",
        "arguments": { "field": "sales", "operator": ">", "value": "100" }
    }
]
```

前端拿到后逐个执行就行：

```javascript
function executeToolCall(call) {
    const args = JSON.parse(call.function.arguments);

    switch (call.function.name) {
        case 'flyTo':
            map.flyTo({ center: geocode(args.location), zoom: args.zoom || 12 });
            break;

        case 'filterMarkers':
            const filtered = allMarkers.filter(m => {
                const v = m.properties[args.field];
                switch (args.operator) {
                    case '>':  return v > Number(args.value);
                    case '<':  return v < Number(args.value);
                    case '=':  return v == args.value;
                    case '>=': return v >= Number(args.value);
                    case '<=': return v <= Number(args.value);
                }
            });
            source.setData(toGeoJSON(filtered));
            break;

        case 'heatmapByField':
            showHeatmap(args.field);
            break;
    }
}

// 执行所有工具调用
for (const call of toolCalls) {
    executeToolCall(call);
}
```

一个重要的实现细节：`filterMarkers` 里应该在前端维护一份全量数据（`allMarkers`），每次筛选是在全量数据上做过滤，而不是在已过滤的结果上再过滤。"先看朝阳区，再看销售额>100万"这种两步筛选，依赖全量数据才能正确叠加条件。

## 地理编码：给 LLM 一把"地名翻译器"

LLM 不知道"朝阳区"在地图上的经纬度是多少。你需要一个地理编码环节把地名转成坐标。

可以接高德/百度/Google 的地理编码 API：

```javascript
async function geocode(placeName) {
    const url = `https://restapi.amap.com/v3/geocode/geo?key=xxx&address=${placeName}`;
    const res = await fetch(url);
    const data = await res.json();
    const [lng, lat] = data.geocodes[0].location.split(',');
    return [Number(lng), Number(lat)];
}
```

如果不想每次都调外部 API（尤其是离线环境），可以自己维护一个地名→坐标的字典，常见的行政区划就那么几级，几百条数据足够覆盖。

更好的做法是把地理编码也作为一个 Function 暴露给 LLM，让 LLM 自己决定什么时候需要查地名：

```javascript
{
    name: 'geocode',
    description: '将地名转换为经纬度坐标',
    parameters: {
        place: { type: 'string', description: '地名' }
    }
}
```

这样 LLM 在 `flyTo('朝阳区')` 之前会先调 `geocode('朝阳区')` 拿到坐标，再传给 `flyTo`。但这个方案会增加 LLM 的调用轮次——每次地名查询多一轮 API 调用，延迟增加约 0.5-1 秒。权衡下来，如果地名种类不多，前端自己维护字典并在 `flyTo` 内部做转换是更快的方案。

## 空间查询的自然语言化

上面只是属性筛选。真正的 GIS 查询应该支持空间关系："三里屯周围 1 公里内的咖啡馆"。

定义一个空间查询函数：

```javascript
{
    type: 'function',
    function: {
        name: 'spatialQuery',
        description: '执行空间查询',
        parameters: {
            type: 'object',
            properties: {
                location: {
                    type: 'string',
                    description: '中心位置地名'
                },
                radius: {
                    type: 'number',
                    description: '半径（米）'
                },
                filter: {
                    type: 'string',
                    description: '额外的属性筛选条件（可选）'
                }
            },
            required: ['location', 'radius']
        }
    }
}
```

当用户说"三里屯周围 1 公里内的咖啡馆"，LLM 输出：

```json
{
    "name": "spatialQuery",
    "arguments": {
        "location": "三里屯",
        "radius": 1000,
        "filter": "type = 'coffee'"
    }
}
```

前端执行时先用 `geocode('三里屯')` 拿到坐标，再调用 Turf.js 的 `buffer` + `pointsWithinPolygon`，或者直接把这个查询转发给后端 PostGIS：

```sql
SELECT * FROM pois
WHERE ST_DWithin(
    geom,
    ST_SetSRID(ST_MakePoint(116.455, 39.932), 4326)::geography,
    1000
) AND type = 'coffee';
```

## 上下文管理：让 LLM 知道地图上有什么

上面的例子基于一个前提：LLM 知道数据有哪些字段。这需要你维护一个 Schema 上下文。

数据字段可以硬编码在 system prompt 里，但更灵活的方案是动态注入——每次发送请求时，从数据源读取当前字段列表：

```javascript
function buildSystemPrompt() {
    const fields = getCurrentDataFields();   // ['name', 'sales', 'region', 'type']
    const zoom = map.getZoom();
    const center = map.getCenter();

    return `你是 WebGIS 系统的自然语言助手。
当前可用数据字段：${fields.join(', ')}。
当前地图缩放级别：${zoom}。
当前视口中心：经度 ${center.lng.toFixed(3)}, 纬度 ${center.lat.toFixed(3)}。
地图上的数据为北京市门店销售数据，时间范围为 2026年7月。`;
}
```

LLM 知道当前缩放级别后，可以智能调整 `flyTo` 的 zoom 参数。知道视口中心后，如果用户说"附近有什么"，LLM 能推断出是以当前视口中心为基准做空间查询。

## 潜在的问题

**幻觉**：LLM 有时会编造不存在的函数名或者参数。生产环境需要做严格的参数校验——函数名必须在白名单里，参数类型和范围必须合法，不符合的直接拒绝执行并返回错误提示。

**延迟**：一次 LLM 调用通常 1-3 秒，加上 Function Calling 的多轮调用可能更久。用户体验上需要有一个 loading 状态——地图上显示一个"AI 理解中..."的指示器。如果 LLM 需要两轮调用（先 geocode 再 flyTo），延迟加起来可能 3-5 秒。可以通过并行调用不互相依赖的 function 来减少延迟。

**成本**：每次查询都要调 LLM，按 token 计费。高频使用下成本需要评估。可以做缓存——同样的 query 返回同样的操作指令，不需要重复调 LLM。但空间查询的参数包含用户当前位置、当前视口等动态信息，缓存命中率不会太高。

这个方向才刚开始，但从用户体验的角度看，本质性的提升已经很明显了：操作路径从"理解地图功能 → 找到对应按钮 → 配置参数 → 执行"变成了"说一句话 → 完成"。这个差距不是一点半点。
