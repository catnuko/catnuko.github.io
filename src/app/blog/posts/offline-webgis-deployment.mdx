给军队、政府、金融机构做项目的 WebGIS 开发者，大概率都遇到过这个场景：客户的环境是完全物理隔离的内网，别说 CDN 了，连你从 GitHub 下载一个 JS 库都要走光盘摆渡。而在这种环境下，你得让地图跑起来，底图、瓦片、字体、图标一个不能少。

这篇文章记录一套经过验证的离线部署方案，从瓦片制作到前端加载全链路打通。

## 全局架构

```
┌─────────────┐     ┌──────────────┐     ┌─────────────────┐
│  PostGIS    │────▶│  T-Rex /     │────▶│  Nginx          │
│  (原始数据)  │     │  tippecanoe  │     │  (静态瓦片服务)   │
└─────────────┘     └──────────────┘     └────────┬────────┘
                                                   │
                                          ┌────────▼────────┐
                                          │  浏览器            │
                                          │  MapLibre GL JS  │
                                          │  (本地 JS/CSS)    │
                                          └─────────────────┘
```

核心思路：把所有外部依赖全部本地化。每一行代码、每一张瓦片、每一个字体文件、每一个图标，都从本地服务器加载。

## 第一步：准备底图瓦片

离线环境不能用高德、百度、Mapbox 的在线底图，必须自己做。

开源底图数据推荐用 OpenStreetMap 的中国区域提取包。国内有几个镜像站提供按国家/省份切好的 `.osm.pbf` 文件，下载后导入 PostGIS：

```bash
osm2pgsql -d gis -U postgres -H localhost china-latest.osm.pbf
```

导入完成后，PostGIS 里就有了 `planet_osm_line`、`planet_osm_polygon`、`planet_osm_point` 等表，包含了道路、建筑、水系、POI 等全量 OSM 数据。

下一步是切片。最直接的工具是 tippecanoe，Mapbox 开源的矢量瓦片切片工具：

```bash
tippecanoe -o china.mbtiles \
    -Z 0 -z 14 \
    --layer=water water.geojson \
    --layer=roads roads.geojson \
    --layer=buildings buildings.geojson
```

参数解释：
- `-Z 0 -z 14`：生成 0 到 14 级的瓦片。14 级对全国数据足够了（每瓦片覆盖约 1.2 公里），再往上瓦片数量爆炸
- `--layer=xxx`：指定图层名和对应的 GeoJSON 数据文件
- 输出是 `.mbtiles`，一个 SQLite 文件，里面按 `z/x/y` 存储了所有矢量瓦片

tippecanoe 的一个坑：它会在低缩放级别自动做要素简化和合并，这个行为有时候不太可控。如果你发现低级别下要素被合并得面目全非，可以用 `--no-feature-limit` 和 `--no-tile-size-limit` 关掉限制，代价是低级别瓦片会很大、加载变慢。更精细的做法是在 GeoJSON 导出阶段就用 PostGIS 的 `ST_Simplify` 控制好精度，不要让 tippecanoe 替你做决策。

mbtiles 文件生成后，需要拆成文件系统上的 `z/x/y` 结构，才能在 Nginx 上直接当静态文件托管。两种做法。

**做法 A：用 mbtiles-server 直接托管**

```bash
npx mbtiles-server china.mbtiles --port 3000
```

好处是省了拆文件这一步。坏处是多了一层 Node.js 服务，增加了部署和维护复杂度。

**做法 B：拆成文件，Nginx 静态托管**

```bash
# 用 mb-util 拆成 z/x/y 目录结构
mb-util --image_format=pbf china.mbtiles tiles
```

拆完后目录结构长这样：

```
tiles/
  metadata.json
  0/
    0/
      0.pbf
  1/
    0/
      0.pbf
      1.pbf
    1/
      0.pbf
      1.pbf
  2/
    ...
```

然后在 Nginx 里配一个静态目录就行：

```
server {
    listen 80;
    server_name tiles.internal;

    location /tiles/ {
        alias /data/tiles/;
        add_header Access-Control-Allow-Origin *;
        add_header Content-Encoding gzip;
    }
}
```

注意 `Content-Encoding: gzip`。PBF 文件本身没有压缩，在 Nginx 层面开 gzip 能把单个瓦片从 50KB 压到 15KB 左右。前提是你的 PBF 文件确实没被预处理过压缩——如果你用的工具已经生成了 gzip 压缩过的瓦片，Nginx 就不要再压一次了，否则浏览器解压会出错。

## 第二步：准备样式文件

有了瓦片数据，还得有样式——告诉前端怎么画道路、水系、建筑。

MapLibre 的样式文件是一个 JSON，定义了数据源、图层、样式规则。在线环境下可以直接引用 MapLibre 的开源样式，离线环境需要自己写。

这个 JSON 的核心结构：

```json
{
  "version": 8,
  "name": "Offline Map",
  "sources": {
    "openmaptiles": {
      "type": "vector",
      "tiles": ["http://tiles.internal/tiles/{z}/{x}/{y}.pbf"],
      "minzoom": 0,
      "maxzoom": 14
    }
  },
  "sprite": "http://tiles.internal/sprites/sprite",
  "glyphs": "http://tiles.internal/fonts/{fontstack}/{range}.pbf",
  "layers": [
    {
      "id": "background",
      "type": "background",
      "paint": { "background-color": "#f8f4f0" }
    },
    {
      "id": "water",
      "type": "fill",
      "source": "openmaptiles",
      "source-layer": "water",
      "paint": { "fill-color": "#a0c8f0" }
    },
    {
      "id": "roads",
      "type": "line",
      "source": "openmaptiles",
      "source-layer": "roads",
      "paint": {
        "line-color": "#ffffff",
        "line-width": 2
      }
    }
  ]
}
```

三个关键的外部资源必须本地化：

`sprite`：地图图标集。MapLibre 用 sprite 来管理地图上的图标（比如 POI 图标、方向箭头）。sprite 由一个 JSON 索引文件和一个 PNG 雪碧图文件组成。一般用开源图标集（比如 MapLibre 官方的 `https://demotiles.maplibre.org/styles/osm-bright-gl-style/sprite`），下载下来放到 Nginx 的 sprites 目录。JSON 索引文件里定义了每个图标的名称、在雪碧图中的位置和大小。

`glyphs`：字体。MapLibre 渲染地图标注时需要字体数据，格式是签名的距离场（SDF）字体。中文标注需要中文字体，不能用默认的英文字体。下载开源的中文 SDF 字体文件（可以从 OpenMapTiles 的仓库获取），也放到 Nginx 目录下，把 glyphs URL 指向本地。SDF 字体的原理是：每个字符被渲染成一个低分辨率位图，但不是存 0/1 的黑白图，而是存每个像素到字形边缘的距离值（有符号距离场）。这样在任意缩放级别下放大缩小都不会模糊。

## 第三步：前端工程离线化

npm 依赖在离线环境下没法装。两种处理思路：

**思路一：构建产物直接拷贝**

在有网的环境下 `npm run build`，把 dist 目录整个拷贝进内网。前端所有依赖都打包进了 bundle.js，不需要 npm install。缺点是每次更新都要在外网构建一次然后拷贝——对于需要频繁修复 bug 的项目很痛苦。

**思路二：npm 离线包**

在有网的环境下用 `npm pack` 把所有依赖打成 tgz，拷进内网后用 `npm install --offline` 安装。比直接拷 dist 灵活，可以在内网做修改和调试。

我个人更习惯思路一，因为离线环境通常不配 Node.js 环境，直接给 Nginx 扔静态文件最简单。

前端代码中使用本地 MapLibre GL JS：

```html
<script src="/lib/maplibre-gl.js"></script>
<link rel="stylesheet" href="/lib/maplibre-gl.css" />
```

不要从 CDN 引入，把 JS 和 CSS 直接放到项目的静态资源目录下跟 Nginx 一起托管。

初始化地图时指向本地样式：

```javascript
const map = new maplibregl.Map({
    container: 'map',
    style: '/styles/offline-style.json',
    center: [116.4, 39.9],
    zoom: 10
});
```

## 第四步：业务数据的离线化

底图搞定了，接下来是业务数据——比如客户自己的管线、地块、设备点位。

方案一：转成 GeoJSON 放 Nginx 静态文件。适合数据量不大且不常变的情况。

方案二：做业务矢量瓦片。用 T-Rex 或者 tippecanoe 把业务 GeoJSON 也切成 PBF，和底图瓦片放一起。前端直接加一个矢量数据源。

```javascript
map.addSource('business-data', {
    type: 'vector',
    tiles: ['http://tiles.internal/business/{z}/{x}/{y}.pbf']
});
```

方案三：TileServer GL 自建服务。如果业务数据经常变动，用静态文件更新麻烦，就起一个 TileServer GL。它可以直接读取 mbtiles 文件或 PostGIS 数据库，提供矢量瓦片和栅格瓦片服务。Docker 部署一行命令：

```bash
docker run -d --name tileserver \
    -v /data:/data \
    -p 8080:80 \
    maptiler/tileserver-gl
```

TileServer GL 带了一个简单的 Web 前端，可以直接预览瓦片效果，适合在部署阶段做验证。

## 常见坑

**跨域问题**。离线环境基本都是 IP 直连或者虚拟机映射，CORS 配不好前端就一直报错。在 Nginx 里所有 `/tiles/`、`/fonts/`、`/sprites/` 的 location 块都要加 `add_header Access-Control-Allow-Origin *`。不要只在 server 块里加一次——子 location 会覆盖父块的 add_header。

**PBF 瓦片 404**。切片的 zoom 范围和前端请求的 zoom 不匹配。比如你切了 0-14，但样式文件里写了 `maxzoom: 18`，前端在 zoom 15+ 时就会疯狂 404。解决方法是样式的 maxzoom 对齐瓦片的实际 zoom 范围。如果非要更高的缩放级别，可以用 `map.setMaxZoom(14)` 限制前端缩放，或者用 overzoom 策略——在大于 14 级时放大 14 级的瓦片，画面会模糊但不会报错。

**中文字体不显示**。MapLibre 默认的字体不包含中文。确认 glyphs 目录下有中文字体的 SDF 文件（注意检查 URL 中 `{fontstack}` 对应的文件夹是否存在），并确认样式文件里 `text-font` 引用的字体名和文件夹名匹配。常见的中文字体栈是 `["Noto Sans CJK SC Regular"]`。

**瓦片太大导致加载慢**。可能是 mbtiles 在低级别下没有做要素简化，导致 z=0 的瓦片包含了全国的道路信息，体积超过 1MB。用 tippecanoe 切的时候加 `--drop-densest-as-needed` 和 `--maximum-tile-bytes=500000`（单个瓦片不超过 500KB）。如果用了自定义工具链，在 PostGIS 导出 GeoJSON 阶段用 `ST_Simplify` 做抽稀，按缩放级别分别导出不同精度。

## 离线部署检查清单

- [ ] 底图瓦片已切好（z=0~14 或你需要的范围），所有 PBF 文件都在 Nginx 静态目录下
- [ ] 样式 JSON 文件已本地化，所有 `tiles`、`sprite`、`glyphs` URL 指向内网地址
- [ ] 图标集（sprite JSON + PNG）已下载并放在内网，路径和样式文件中的 sprite URL 一致
- [ ] 中文字体 SDF 文件已放在内网，glyphs URL 指向正确
- [ ] MapLibre GL JS 的 JS/CSS 文件已本地化，不依赖任何 CDN
- [ ] Nginx 配好了 CORS 头（所有静态资源路径都要加）
- [ ] 前端代码中没有任何外部网络依赖（检查所有 import 和 script 标签的 src）
- [ ] 在内网环境实际测试了完整流程——打开页面、拖拽缩放地图、查看瓦片是否正常加载
