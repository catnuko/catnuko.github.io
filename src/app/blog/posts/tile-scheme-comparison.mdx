底图瓦片方案的选择是一个"看起来简单、选错了想死"的决策。一个省级地图项目，z=0~14 的栅格瓦片大概 20GB、几百万个文件，矢量瓦片大概 2GB、同样的文件数。存储成本差十倍，但前端渲染压力也差十倍。没有绝对正确的答案，只有对你场景最合适的。

这篇文章把三种方案从头到尾比一遍，包括成本、性能、维护复杂度。

## 栅格瓦片

**是什么**

预渲染的图片。服务器上存的是 PNG 或 JPEG 文件，前端按 `z/x/y` 请求对应的图片，贴到地图上。就这么简单。

**生成方式**

```bash
# 用 GeoServer 的 GeoWebCache 自动生成
# 或者用 gdal2tiles 从一张大图直接切
gdal2tiles.py -z 0-14 china.tif tiles/
```

GeoServer + GeoWebCache 是目前最成熟的栅格瓦片方案。GeoWebCache 会自动缓存 WMS 的请求结果——第一次请求 z=12/x=3423/y=1568 时，GeoServer 渲染这个瓦片（从 PostGIS 读取该范围内的矢量数据，按 SLD 样式画图），生成一张 PNG 存下来。后续请求同一个瓦片直接返回缓存的 PNG，不再渲染。

**优点**

简单。简单到出问题时几乎不需要排查——文件在服务器上就能看到，404 就是没了，加载慢就是图片太大，缩小图片尺寸就能解决。

兼容性好。栅格瓦片本质就是图片，任何地图库都支持。Leaflet、OL、MapLibre、甚至一个 `<img>` 标签都能加载。

后端零渲染压力。瓦片是预生成的，后端就是一个 Nginx 静态文件服务，不需要运行 GeoServer 或其他地图渲染服务。一台不到 100 块的虚拟机就能支撑几百人同时访问。

**缺点**

存储大。一套 z=0~14 的全球底图大约 10-20GB。如果做到 z=0~18（城市级别需要的精度），文件数量从几十万涨到几千万，存储从 20GB 涨到 2TB。这还只是一套样式。

样式改不了。瓦片是渲染死的。想要深色模式？重新切一套。想要黑夜模式？再切一套。三套样式就是三倍存储。

高 DPI 尴尬。Retina 屏需要 @2x 的瓦片（每张 512×512 代替 256×256），存储再翻倍。而且 @2x 瓦片在高分屏上清晰了，在普通屏上浪费带宽——你没法让同一个 URL 根据设备 DPR 返回不同分辨率的图片。

**适用场景**：底图样式固定、不需要频繁切换、内网或低带宽环境。纯展示型项目（不需要交互式样式变化）用栅格瓦片是性价比最高的。

## 矢量瓦片

**是什么**

数据，不是图片。服务器存的是 PBF（Protocol Buffer Binary）格式的矢量数据——道路的几何坐标、水系的边界、POI 的名称和分类。前端下载后，用自己的渲染引擎（MapLibre GL JS 或 Deck.gl）实时渲染成地图。

**生成方式**

```bash
# 用 tippecanoe 从 GeoJSON 生成 mbtiles
tippecanoe -o china.mbtiles -Z 0 -z 14 water.geojson roads.geojson poi.geojson

# 拆分成文件
mb-util --image_format=pbf china.mbtiles tiles/
```

生成的 PBF 文件只包含矢量数据，没有颜色、没有线宽、没有字号。这些都由前端的样式文件（style.json）决定。

**优点**

体积小。同样是 z=0~14 的全国范围，矢量瓦片约 1-2GB（不到栅格的十分之一），因为矢量几何比同样精度的栅格图片紧凑得多——一条道路存几个坐标就够了，栅格要存几百个像素。

样式自由。一套瓦片数据可以渲染出无数种样式——浅色、深色、高对比度、卫星图叠加。改样式不需要重新切瓦片，只需要改 style.json 文件然后刷新浏览器。甲方说"底色太白了"，你改一行 JSON，两秒钟见效。

无极缩放。矢量数据是分辨率无关的。z=14.5 这种中间级别，栅格瓦片只能放大 z=14 的图片然后模糊了事，矢量瓦片可以用 z=14 的几何数据精确重绘，边缘仍然锐利清晰。

动态标注。因为标注和地图数据分离，可以在渲染时动态调整——缩放级别变高时地名逐渐浮现，道路名称的密度自动调整避免重叠。栅格瓦片的标注是刻在图片上的，改不了。

**缺点**

前端渲染压力大。矢量瓦片的渲染全在前端——数据下载、protobuf 解码、样式匹配、GPU 绘制。手机端渲染全国范围的矢量底图，低端机可能掉到 20 FPS 以下。

开发复杂度高。样式的调试比较耗时——你要在 Maputnik 里调几十个图层，或者直接手写几千行的 style.json。标注的密度控制、防重叠、图层的绘制顺序——每一个细节都可能出问题。

浏览器兼容要求高。矢量瓦片依赖 WebGL。IE 完全不用考虑，一些老旧的 WebView（比如部分政务系统内嵌的 IE 内核浏览器）也跑不了。

**适用场景**：需要多种样式、对美观度要求高、以桌面端为主的项目。如果你有一个 UI 设计师会调样式，矢量瓦片能让地图跟整个系统的 UI 风格完全统一——这是栅格瓦片做不到的。

## PMTiles

**是什么**

一个这两年冒出来的新方案。PMTiles（Pyramid Map Tiles）把几百万个瓦片文件打包进一个文件——底层就是一个支持 HTTP Range Request 的归档格式。前端发出一个 HTTP 请求，带 `Range: bytes=xxxx-yyyy` 头，只读取需要的字节，服务器返回对应的瓦片数据。

本质上是把"几百万个小文件"和"一个大文件"这两种存储方式的优点结合到一起。管理一个文件比管理几百万个文件方便一万倍，但通过 Range Request 又能做到零延迟的按需读取。

**生成方式**

```bash
# 从 mbtiles 转成 pmtiles
pmtiles convert china.mbtiles china.pmtiles

# 或者用 tippecanoe 直接输出 pmtiles
tippecanoe -o china.pmtiles -Z 0 -z 14 data.geojson
```

**部署方式**

直接把 `china.pmtiles` 扔到对象存储或 CDN 上：

```
https://tiles.example.com/china.pmtiles
```

前端加载：

```javascript
// MapLibre GL JS 的 pmtiles 插件
import { Protocol } from 'pmtiles';

const protocol = new Protocol();
maplibregl.addProtocol('pmtiles', protocol.tile);

map.addSource('china', {
    type: 'vector',
    url: 'pmtiles://https://tiles.example.com/china.pmtiles'
});
```

**优点**

部署简单到离谱。不需要拆文件、不需要建目录、不需要配 Nginx 的 location 规则。一个文件扔上去就完事。这对运维来说是天大的好消息——尤其是那种每次发版都要提交运维工单、等审批、等部署的环境。

支持栅格和矢量两种模式。PMTiles 只是一个容器格式，不关心里面装的是 PNG 还是 PBF。所以你可以用它打包栅格瓦片，也可以打包矢量瓦片。

传输效率高。PMTiles 内部有目录索引——前端请求 z=12/x=3423/y=1568 时，PMTiles 协议会先从文件尾部的目录区查出这个瓦片在文件中的字节偏移，然后用 Range Request 精确读取。一个瓦片通常几十到几百 KB 的 HTTP 请求，延迟不超过 200ms。

**缺点**

依赖 HTTP Range Request。服务器必须支持 Range 头。大部分对象存储（S3/OSS/COS）和 CDN 都支持，但某些古董级的静态文件服务器可能不支持。如果用 CloudFront + S3 或阿里云 CDN + OSS 这种标准组合，没问题。如果是一个内部的老旧 FTP 服务器，不行。

前端库支持还不广。MapLibre 有官方插件，OpenLayers 有社区插件，Leaflet 还没有正式支持。Cesium 的 3D Tiles 不能直接用 PMTiles——3D Tiles 有自己的 LOD 加载协议，跟 z/x/y 的瓦片模型不兼容。不过对于 2D 和 2.5D 的底图场景，PMTiles 是个很好的选择。

## 三维方案对比

| | 栅格瓦片 | 矢量瓦片 | PMTiles |
|---|---|---|---|
| 存储体积（z=0~14 全国） | ~20GB | ~2GB | ~2GB（同矢量） |
| 文件数量 | 几十万 ~ 几百万 | 几十万 ~ 几百万 | **1 个** |
| 前端渲染压力 | 几乎为零 | 中等到高 | 中等到高（同矢量） |
| 样式可定制性 | 无（需重新切） | 极高 | 极高（同矢量） |
| 高 DPI 支持 | 需要 @2x 瓦片 | 原生矢量，自动适配 | 原生矢量，自动适配 |
| 无极缩放 | 模糊 | 清晰 | 清晰（同矢量） |
| 部署复杂度 | 高（大量文件） | 中等到高（大量文件） | **极低（1 个文件）** |
| 离线使用 | 容易（拷贝文件夹） | 中等 | 容易（1 个文件） |
| 渐进式加载 | 支持（低级别大范围先加载） | 支持 | 支持 |
| 浏览器兼容 | IE 也能用 | 需要 WebGL | 需要 WebGL |

## 选型建议

起步阶段或小项目 → **PMTiles + 矢量瓦片**。省掉拆文件和部署的烦恼，而且随时可以切换到传统的文件式矢量瓦片服务——PMTiles 文件本质上就是个 mbtiles 的镜像格式，你随时可以把它拆成 z/x/y 目录。

需要高兼容性 → **栅格瓦片**。如果用户群体里有老旧浏览器或者各种奇怪的 WebView，栅格是最低公分母。可以在项目中同时提供栅格和矢量两个图层组——新浏览器加载矢量，检测到不支持 WebGL 就降级到栅格。

离线/内网部署 → **PMTiles**。拷贝一个文件比拷贝几十万个文件快太多了。我之前做内网项目，用 U 盘拷栅格瓦片，拷到一半 Windows 资源管理器直接卡死——几百万个小文件的 I/O 太慢。PMTiles 一个文件几 GB，拷完就走。

如果选了矢量瓦片，同时也想要 PMTiles 的部署便利 → 可以同时提供两种访问方式。PMTiles 文件直接挂到 Nginx 上，再配一个路径把同一个文件映射成 z/x/y 格式的 URL。这样需要 z/x/y 的老代码能继续跑，新代码可以直接用 PMTiles 协议。
