入职第一周，Leader 扔过来一个需求：在 OpenLayers 地图上把后台返回的经纬度标出来。这能有多难？照着文档撸了个 Marker，结果点全跑到了海里。明明经纬度没问题，地图中心也对，就是偏——往东南方向偏了大概几百米。

后来才知道，这就是 WebGIS 入门必踩的第一坑：坐标系。

## 问题出在哪

大部分 Web 地图（Google Maps、高德、百度、Mapbox、OpenStreetMap）默认用的都是 EPSG:3857，也就是俗称的"Web 墨卡托"。而后台接口返回的经纬度，通常是 GPS 设备采集的 WGS84 坐标，也就是 EPSG:4326。

这两个坐标系看着都是经纬度，但它们的"世界观"不一样。你把 WGS84 的数据直接丢给 Web 墨卡托的地图，地图会把你的经纬度当成墨卡托的米坐标来解析，点不偏才怪。

打个比方：你拿着一张按真实比例画的世界地图，往一面哈哈镜前面一站，哈哈镜里反射出来的位置当然不对。WGS84 是那张真实地图，Web 墨卡托就是那面哈哈镜。

## WGS84（EPSG:4326）是什么

WGS84 全称 World Geodetic System 1984，是美国国防部建立的一个地心坐标系。它把地球近似成一个椭球体，用经度（longitude）和纬度（latitude）来表示位置。GPS 芯片出来的原始数据就是 WGS84 坐标。

几个关键数字：

- 赤道半径（长半轴）：6378137.0 米
- 极半径（短半轴）：6356752.3142 米
- 扁率：1 / 298.257223563

WGS84 覆盖全球，经度范围 [-180, 180]，纬度范围 [-90, 90]。它是一个地理坐标系（Geographic Coordinate System），用角度做单位。

北京的坐标大概是 [116.397, 39.908]。注意，经度在前，纬度在后。很多新手在这个顺序上栽过跟头——GeoJSON 规范里是 [lng, lat]，但有些系统用的是 [lat, lng]，搞反了你的点就跑到了南极附近。

## Web 墨卡托（EPSG:3857）又是什么

Web 墨卡托本质上是墨卡托投影的一个变体。墨卡托投影是 1569 年荷兰人墨卡托发明的，核心思路是把地球表面投影到一个圆柱面上，然后展开成平面。这样做的好处是保持了方向角不变——也就是说地图上任意两点连线的角度跟实际航行角度一致，所以航海图用了它几百年。

但原始的墨卡托投影用的是 WGS84 椭球体模型，计算比较复杂。Google 在 2005 年推出 Google Maps 时做了一个"偷懒"的优化：把地球当成完美球体来算投影，半径直接取 WGS84 长半轴 6378137.0 米。

这个简化带来的误差有多大？在赤道附近不到 0.1%，但在高纬度地区会达到 0.3% 左右。对日常导航和地图浏览来说完全可以接受，但对测绘级精度的应用就不够了。

后来这个"偷懒版"被业界广泛接受，EPSG 给了它一个正式编号 3857，也叫做 Pseudo-Mercator（伪墨卡托）或者 Popular Visualisation CRS。

在 EPSG:3857 下，坐标单位是米。原点（0, 0）在赤道与本初子午线的交点。X 轴向右（东）为正，Y 轴向上（北）为正。整个世界的范围大约是 [-20037508.34, -20037508.34] 到 [20037508.34, 20037508.34]。

## 经纬度怎么变成米坐标

墨卡托投影的数学公式其实不复杂。

先把经纬度从度转成弧度：

> lon_rad = lon × π / 180
>
> lat_rad = lat × π / 180

然后用球体墨卡托公式：

> x = R × lon_rad
>
> y = R × ln( tan(π/4 + lat_rad/2) )

其中 R = 6378137。

第一个公式很好理解：经度直接乘以地球半径，就得到了水平方向的距离。

第二个公式需要稍微解释一下。tan(π/4 + lat_rad/2) 这个函数在纬度从 -90° 到 90° 变化时，值从 0 增长到无穷大。取对数后，纬度被映射到了一个有限的区间。这就是为什么在墨卡托投影下，格陵兰岛看起来比非洲还大——高纬度地区被大幅拉伸了。

用 Python 写一个验证：

```python
import math

R = 6378137.0

def lnglat_to_mercator(lng, lat):
    x = R * math.radians(lng)
    y = R * math.log(math.tan(math.pi / 4 + math.radians(lat) / 2))
    return x, y

# 北京天安门
x, y = lnglat_to_mercator(116.397, 39.908)
print(f"X: {x:.2f}, Y: {y:.2f}")
# 输出：X: 12958879.93, Y: 4854834.74
```

反过来，墨卡托转 WGS84：

```python
def mercator_to_lnglat(x, y):
    lng = math.degrees(x / R)
    lat = math.degrees(2 * math.atan(math.exp(y / R)) - math.pi / 2)
    return lng, lat
```

## 前端怎么处理

OpenLayers 默认的视图坐标系是 EPSG:3857。如果你的数据是 EPSG:4326，有两种处理方式：

**方式一：让图层自己转**

```javascript
// 创建一个 WGS84 数据源
const source = new VectorSource({
  features: new GeoJSON().readFeatures(geojsonData, {
    dataProjection: 'EPSG:4326',    // 数据本身的坐标系
    featureProjection: 'EPSG:3857'  // 地图的坐标系
  })
});
```

`dataProjection` 告诉 OL 你的原始数据是什么坐标系，`featureProjection` 告诉 OL 你要把它转成什么坐标系。OL 内部会调用 Proj4js 做转换。

**方式二：用 Proj4js 手动转**

```javascript
import proj4 from 'proj4';

// 定义两个坐标系
const wgs84 = 'EPSG:4326';
const webMercator = 'EPSG:3857';

// 单个点转换
const [x, y] = proj4(wgs84, webMercator, [116.397, 39.908]);
console.log(x, y); // [12958879.93, 4854834.74]
```

Leaflet 稍微特殊一点。Leaflet 默认就工作在 EPSG:3857 下，而且它的 LatLng 类本身就是用经纬度表示的，内部会自动转换。所以你在 Leaflet 里创建 Marker 直接用经纬度就行：

```javascript
L.marker([39.908, 116.397]).addTo(map);
```

注意 Leaflet 用的是 [lat, lng] 顺序，跟前端其他库 [lng, lat] 刚好反过来。这也是一个高频踩坑点。

## 中国特有的坐标系问题

上面讲的是国际通用的 WGS84 和 Web 墨卡托。在国内做 GIS，还绕不开两个坐标：GCJ-02 和 BD-09。

GCJ-02 是国家测绘局制定的加密坐标系，也叫火星坐标系。它在 WGS84 的基础上加了一个非线性的偏移算法，偏移量在不同地区不一样，一般在几十到几百米之间。国内所有合法地图服务（高德、腾讯、天地图）都必须使用 GCJ-02。

BD-09 是百度在 GCJ-02 基础上又加了一层加密，只用在百度地图上。

所以你拿 GPS 设备（WGS84）采集的经纬度直接丢到高德地图上，会偏；丢到百度地图上，偏得更多。

前端处理这个问题的标准做法是用坐标转换库。比较常用的有 `coordtransform`：

```javascript
import coordtransform from 'coordtransform';

// WGS84 转 GCJ-02
const gcj = coordtransform.wgs84togcj02(116.397, 39.908);
// [116.403, 39.911]

// GCJ-02 转 BD-09
const bd = coordtransform.gcj02tobd09(116.403, 39.911);
// [116.410, 39.917]
```

注意这个库的转换精度不是 100% 准确的——毕竟火星坐标的加密算法并未公开，是通过逆向工程拟合出来的。对日常导航和展示够用，对测绘级精度不够。

在实际项目中，你需要搞清楚：
- 后端存的坐标是什么坐标系？（通常会是 GCJ-02 或 WGS84）
- 你用的是什么地图底图？（高德是 GCJ-02，Google 是 WGS84，百度是 BD-09）
- 是否需要在前端做转换，还是后端已经转好了？

这三个问题在项目启动时就该跟团队对齐。我见过不少项目上线后发现点位偏移，追查半天才发现是坐标系没对齐。

## 瓦片坐标与缩放层级

理解了坐标系之后，再看瓦片地图的运作方式会更清晰。

地图被切成一个个 256×256 像素的正方形瓦片。在缩放级别 z 下，整个世界被分成 2^z × 2^z 个瓦片。

把 EPSG:3857 的米坐标转成瓦片坐标：

```javascript
function metersToTile(x, y, z) {
    // 世界总范围（米）
    const worldSize = 256 * Math.pow(2, z);
    const originX = -20037508.34;
    const originY = 20037508.34;
    const resolution = (originY - originX) / 256 / Math.pow(2, z);

    const tileX = Math.floor((x - originX) / (256 * resolution));
    const tileY = Math.floor((originY - y) / (256 * resolution));

    return { tileX, tileY };
}
```

在 z=10 的时候，全球被切成 1024×1024 张瓦片，每张大约覆盖 3.9 万米的区域。到了 z=18，就是 26 万×26 万张，每张覆盖约 150 米。

这个瓦片机制决定了地图的加载策略：视口内需要哪些瓦片，就请求哪些瓦片。超出视口的不会加载，这就是为什么你在地图上快速拖拽时会看到一片灰色——新瓦片还没来得及加载。

## 总结

坐标系问题是 WebGIS 的基础，但也是生产中出问题最多的地方。三个要点记住就行：

1. 后端返回的经纬度是什么坐标系？WGS84 / GCJ-02 / BD-09？搞清楚，别猜。
2. 前端地图用的是什么坐标系？EPSG:3857 是主流，但别忘了国内地图服务底层走的是 GCJ-02。
3. 经纬度顺序是 [lng, lat] 还是 [lat, lng]？不同库不一样，以文档为准。

把这些理清楚，你的点就再也不会飘到海里了。
